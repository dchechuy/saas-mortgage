# Phase 1 — Tenant Schema and Safe Migration

You are working on `saas-mortgage` (Cophy Portal).

Read the following before starting:

- `docs/prompts/Tenant Separation - PRD.md`
- `docs/ARCHITECTURE.md`
- Any repository agent instructions that apply

Implement only Phase 1. Do not add the tenant switcher or broadly rewrite route queries in this phase.

---

## Goal

Create the tenant data foundation and migrate all existing records without data loss:

- Cofficiency is the protected internal tenant.
- AdvantageFirst owns all existing business/configuration data and all historical logs.
- The existing system `admin` user belongs to Cofficiency.
- Every other existing user belongs to AdvantageFirst.
- The existing admin's remembered active tenant is AdvantageFirst.

---

## Required model changes

### Add `Tenant`

Add a `Tenant` model with:

- `id`
- globally unique `name`
- globally unique stable `slug`
- `is_active`
- `is_protected`
- `created_at`
- `updated_at`

Add useful relationships only where they improve clarity without creating ambiguous foreign keys.

### Update `User`

Add:

- required `tenant_id` for immutable home tenant
- nullable `last_active_tenant_id`
- explicit relationships using `foreign_keys` because both columns point to `tenant`

Do not add a user/tenant membership join table.

### Add required `tenant_id`

Add a non-null tenant foreign key to:

- `LlmModel`
- `Attribute`
- `Integration`
- `AiAgent`
- `AgentConversation`
- `LlmRequestLog`
- `UserActivityLog`
- `ApiRequestLog`

Do not add redundant tenant columns to `AgentMessage` or `MessageAttachment`; they inherit ownership from `AgentConversation`.

### Add `TenantFeatureFlag`

Create the per-tenant override model described in the PRD, unique on `(tenant_id, feature_flag_id)`.

### Update uniqueness

Replace global business-data uniqueness with:

- `LlmModel`: `(tenant_id, name)`
- `Attribute`: `(tenant_id, category, name)`
- `Integration`: `(tenant_id, name)`

Keep `User.username`, `User.email`, `Tenant.name`, and `Tenant.slug` globally unique.

## Alembic migration

Create a hand-reviewed migration. Do not rely blindly on autogenerated constraint changes, especially with SQLite.

Migration order:

1. Create `tenant`.
2. Insert `Cofficiency` / `cofficiency` with `is_protected=true`.
3. Insert `AdvantageFirst` / `advantagefirst`.
4. Add tenant columns as nullable.
5. Create `tenant_feature_flag`.
6. Find the existing system user with username `admin` and assign its home tenant to Cofficiency.
7. Assign every other existing user to AdvantageFirst.
8. Set the existing admin's `last_active_tenant_id` to AdvantageFirst.
9. Assign every existing model, attribute, integration, agent, and conversation to AdvantageFirst.
10. Assign every existing user activity, LLM request, and API request log to AdvantageFirst, regardless of actor.
11. Replace affected unique constraints with tenant-relative constraints.
12. Make required tenant columns non-null.

Make the migration compatible with the database patterns already used by this repository. Preserve row counts and foreign keys. Supply a valid downgrade where safely possible; document any unavoidable downgrade limitation.

Update `app/__init__.py` imports and seed guards so application startup does not race or insert partially migrated data. Do not move migration-only backfill behavior into normal startup seeding.

---

## Invariants

- A user's home tenant is conceptually immutable after creation. Model code may expose a read-only convenience property, but route enforcement comes in Phase 3.
- `AgentConversation.tenant_id` is required even though ownership is also related to user/agent.
- No tenant-owned row may remain null after upgrade.
- Do not reattribute historical logs to the actor's new home tenant. Every historical log belongs to AdvantageFirst.
- Release notes, roles, permissions, navigation layout, documentation prompts, and the feature flag catalogue remain global.

## Tests

Add or extend the repository's test setup to cover:

1. Migration creates exactly one Cofficiency and one AdvantageFirst tenant.
2. Cofficiency is protected.
3. Existing admin home tenant is Cofficiency.
4. Existing non-admin users are AdvantageFirst.
5. Existing admin remembered tenant is AdvantageFirst.
6. Existing tenant-owned records are AdvantageFirst.
7. All historical log types are AdvantageFirst even when actor is admin.
8. Required tenant columns are non-null.
9. Tenant-relative uniqueness allows the same natural name in two tenants and rejects duplicates within one tenant.
10. Model relationships load without ambiguous-foreign-key errors.

Run the full available test suite and `flask db upgrade` against a disposable database. Also run `flask db downgrade`/upgrade when supported.
